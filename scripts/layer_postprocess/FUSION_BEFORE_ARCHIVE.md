# v12：先用深层内容融合，再确定主体和归档

## 修复的问题

v11 虽然修复了深层细节展平进第四层的问题，却先将 L5+ 放入归档，再向模型生成分组候选，丢失了深层内容作为融合材料的机会。v12 恢复完整候选树参与融合；不撤销 v11 的严格补缺。

## 执行顺序

1. 复用 top_down_cleanup（仅收缩）、normalize（preserve_meaningful_deep）进行几何清理。它们可以收缩冗余包装，但不按四层上限批量删除有意义的细节。
2. 保存 fusion-input-hierarchy.json：这是归档前完整的规范化树。规则从各深度产生密度触发的兄弟分组与固定上层替换方案；图片仍用原始完整截图。
3. 一次模型请求提供原始框注册表、完整树、固定融合候选和像素候选。不额外调用“归档层重建”模型，不把模型视作全树真值审核。
4. 已批准替换按原方案上层深度由深到浅执行，模型数组顺序不决定执行顺序。执行每项前再次检查实际树；成员冲突或方案失效要拒绝并记录，不随意修改。复用已有下层区域，或以成员外接区域替换/拆解上层；保留旧成员不得加深。
5. 复用已有包装收缩后，才执行 accumulate_to_fourth 严格选择 L1–L4 主体，未选细节进入非训练 L5 档案。旧 drop 配置不能在融合期间删掉深层证据。
6. 修复归档 owner 关联，验证主体 parent/层级和坐标，保存正式结果与审计。

## 示例

原 L4 大容器 U，内部 L5 有标题 A、图片 B、远处控件 C。若 A+B 为合理视觉组：

- 由规则提出 A+B，模型确认；新区域 G 占用 U 的第四层位置。
- U 收缩为剩余 C 的区域；若成为冗余单子包装，可以复用 C 替代它。
- A/B 原框、原层级、原 parent 保存在 L5 档案，owner 指向 G。
- 不把 U、G、A、B 全部铺成第四层兄弟；不为 G 再额外增加一层。

## 查看与审计

- fusion-input-hierarchy.json：完整实际融合输入，可能超过四层，仅诊断使用。
- rule-hierarchy.json：对未融合输入做严格四层筛选的对照预览，不能回流为模型输入。
- candidate-hierarchy.json / hierarchy.json：实际批准融合后再筛选的结果。
- layer-review.json：fusion_input、deep_group_candidates、pre_archive_fusion、applied_upper_replacements 以及最终 layer_accumulation。
- compare.py：查看页详情包含融合输入摘要、归档前结果与实际上层替换记录。

dry-run 不调用模型，不执行融合批准；只保存完整输入、候选与四层对照预览。它只能证明深层材料可用，不能证明分层视觉效果改善。

## 边界

这是恢复既有密度触发、同父候选和固定替换机制；不是任意跨父聚类，也不是无限轮动态重提名。未触发规则、候选不适用或模型拒绝时，原有主体仍按严格补缺保留，细节留档。结构通过不代表语义准确。

版本 visual_layers_fuse_before_archive_v12，旧版本模型响应不直接复用。
